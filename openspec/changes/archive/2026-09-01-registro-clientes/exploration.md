## Exploration: BACKLOG.md item #12 — Client registration with transactional profile creation

### Current State

The repository contains a NestJS/Fastify API with the global `/api/v1` prefix, a `CatalogsModule` exposing active categories and districts, and in-process Fastify injection tests. Catalog services inject the process-scoped `PrismaService`; there is no registration module, authentication guard, JWT verifier, or provider adapter. `app.factory.ts` exposes an offline export bootstrap, but it does not yet provide a general provider-override option.

The identity migration and Prisma schema already provide `User`, `ClientProfile`, and `District`. `users.email` and `users.auth_subject` are unique; client profiles have required name, E.164 phone, and district fields; the database has a client-profile role trigger and restrictive foreign keys. The district table has an `active` flag, but the foreign key alone does not enforce active-only selection. The existing service tests use fakes and spies; no test connects to PostgreSQL.

The global problem filter already maps HTTP 409 to `CONFLICT` and emits safe `application/problem+json`, but there is no explicit Prisma `P2002` duplicate-email mapper. A registration service must map both a friendly pre-read and the final unique-constraint race to the same safe conflict without exposing credentials, `authSubject`, SQL, or provider details.

OpenAPI is generated from Nest metadata by `npm run contract:export`, client types are generated by `npm run contract:generate`, and freshness/validity/type checks run through `npm run contract:check` (with `contract:validate`, `contract:diff`, and workspace typecheck available separately). A new registration surface therefore requires DTO metadata, regenerated `apps/api/openapi.json`, regenerated `packages/api-client/src/generated.ts`, and the existing contract gates.

Supabase Auth is not integrated and the Supabase project is a recorded pending gate. The current environment schema consumes only foundation and database values. `docs/environments.md` lists `AUTH_ISSUER_URL` and `AUTH_JWKS_URL` as future, not-consumed values; no frozen Auth admin service-key variable exists. The repository must not pretend that a live provider, email verification, or executed PostgreSQL transaction has been tested offline.

#### Binding decisions from TECH-DESIGN.md and ADRs

The following decisions are locked and should not be re-decided by the proposal:

> “Supabase Auth administrará credenciales, sesiones, recuperación y emisión de tokens.” — `TECH-DESIGN.md` §3.3 / ADR-0006

> “El rol de dominio y los datos de perfil se almacenarán en las tablas de la aplicación; la API no confiará para autorizar en metadatos editables enviados por el cliente.” — ADR-0006

> “El correo almacenado en `users` es una copia de consulta sincronizada al establecer sesión; identidad, verificación y cambios de correo se resuelven desde Supabase Auth.” — `TECH-DESIGN.md` §5.3

> “Tras la primera sesión verificada, la API crea de forma idempotente `users` con el rol elegido una sola vez.” — `TECH-DESIGN.md` §8.1

> “La API NestJS recibe únicamente tokens entre servidores.” — `TECH-DESIGN.md` §7.2

> “Las transacciones no contienen llamadas de red ni procesamiento de archivos.” — `TECH-DESIGN.md` §11

> “Se añadirá la entidad `districts` con identificador interno, código UBIGEO único, nombre, provincia, departamento y estado activo.” — ADR-0018

> “`client_profiles` y `requests` referenciarán un distrito activo mediante clave foránea” — ADR-0018

> “`409` para estado o concurrencia incompatible” — `TECH-DESIGN.md` §7.1

The sources leave a material seam unresolved: §7.2 omits a registration/onboarding path, while §8.1 places domain-user creation after a verified session. The requested client slice resolves the persistence responsibility—create `users` and `client_profiles` atomically—but the proposal must explicitly name the API route and decide who invokes Supabase Auth and when.

### Affected Areas

- `apps/api/src/registration/` — new client-registration module with concrete request/response DTOs, controller, application service, and provider-port types. The API contract should accept a trusted identity context plus complete client profile data; it must not persist a password.
- `apps/api/src/app.module.ts` — register the registration module without changing catalog behavior.
- `apps/api/src/app.factory.ts` and registration test setup — expose an injectable auth-provider seam or test override so fake identity results can be used by `server.inject` tests without Supabase.
- `apps/api/src/common/errors/` — add a narrowly scoped duplicate-email/P2002 translation if the existing filter is insufficient. All paths must use the existing stable `CONFLICT`, `SEMANTIC_INVALID`, `DEPENDENCY_UNAVAILABLE`, and `INTERNAL_ERROR` mappings.
- `apps/api/src/config/env.schema.ts` and `AppConfigService` — no change under the recommended deferred provider seam. Add an environment value only when a real adapter consumes a previously agreed name; do not invent an Auth admin secret merely to make offline tests pass.
- `apps/api/openapi.json` — regenerate the implemented registration/onboarding path and its DTO/error responses from Nest metadata.
- `packages/api-client/src/generated.ts` — regenerate typed paths and schemas; `packages/api-client/src/client.ts` remains a transport-only factory and must not gain cookie, session, token, or business logic.
- `apps/api/src/registration/*.spec.ts` and an integration spec — add fake-Prisma, fake-provider, and Fastify injection coverage. Existing identity schema/migration tests remain unchanged and continue to be static evidence.
- `apps/api/prisma/schema.prisma` — normally no model change is needed; the existing unique email, client-profile FK, role trigger, and district relation are the persistence boundary for this feature.

### Boundary Analysis

**In scope:** one client registration/onboarding API contract; client request validation; email normalization; trusted auth-subject/email handoff; active-district validation; one short Prisma transaction creating `User` and `ClientProfile`; safe duplicate-email 409 handling; provider seam and fake adapter; OpenAPI/client regeneration; offline unit and injection tests.

**Out of scope:** web forms and responsive UI; Next.js BFF implementation; login, refresh, logout, cookies, CSRF, and JWT/JWKS verification in #13; profile editing in #14; email-verification UX and recovery flows; live Supabase provisioning; live PostgreSQL migration/transaction/trigger proof; request creation and #18 UI behavior; technician profile fields and specialties.

BACKLOG item #12 itself mentions both client and technician registration, but this named change is specifically the client path. There is no separate technician-registration backlog item; technician onboarding must not be silently added to this client slice. If item #12 is required to close both roles, the proposal should make technician registration a separately reviewable work unit rather than adding technician fields, specialties, and profile-completeness rules here.

### Approaches

1. **Supabase/BFF first, verified client onboarding API (recommended)** — the future same-origin web/BFF flow creates the unverified Supabase Auth account and handles verification; after a verified session, a trusted auth adapter invokes a versioned client-onboarding command. The API derives `authSubject` and provider email from the trusted identity context, then creates the domain user and complete client profile in one database transaction.
   - Pros: follows ADR-0011 and §8.1; keeps credentials out of the API persistence boundary; keeps network calls outside the transaction; naturally reconciles an Auth account that exists before a domain row; supports a fake identity context offline.
   - Cons: the BFF/JWT seam and Supabase project are not available in this change; end-to-end visitor registration cannot be claimed; the exact onboarding route and verified-identity interface must be frozen in the proposal.
   - Effort: Medium.

2. **API provider-first orchestration** — the API accepts registration credentials, calls an injected Supabase admin adapter outside the transaction, then creates `User` and `ClientProfile` in one transaction using the returned subject and provider email.
   - Pros: one API-facing signup operation; fake provider tests can cover the orchestration; the API can return a provider-pending-verification result.
   - Cons: raw passwords cross the API process; a successful Auth call followed by a failed database transaction creates an orphan provider account; compensation/deletion is another remote failure; it conflicts with the token-only API boundary and requires an unapproved Auth admin secret; a live provider cannot be verified now.
   - Effort: High.

3. **Database-first placeholder subject with deferred Auth** — create the user/profile transaction using a test or temporary `authSubject`, and connect the provider later.
   - Pros: completely offline and simple to test; proves the requested database transaction immediately.
   - Cons: cannot satisfy real verification or trusted identity; a placeholder subject is an authorization risk; duplicate-email behavior can diverge from Supabase; it would be unsafe as a public production registration endpoint.
   - Effort: Low initially, High follow-up risk.

### Transaction and Error Contract

The recommended API operation is a trusted client onboarding command, not a password storage endpoint. Its logical input is complete client profile data (`name`, `phone`, `districtId`) plus provider-derived identity context. It returns a sanitized domain projection and never returns a password, token, provider secret, or internal subject. The exact path and 201-versus-idempotent-repeat status remain proposal decisions.

Inside one short Prisma transaction:

1. Normalize the provider email and verify the trusted identity is verified and has the requested client role.
2. Read the normalized email and provider subject for reconciliation; a different existing user with the same normalized email is a generic 409.
3. Lock or revalidate the requested district as active. Nonexistent or inactive districts produce 422 `SEMANTIC_INVALID` with `fieldErrors.districtId`.
4. Create `User` with role `CLIENT` and a complete nested `ClientProfile`, or reconcile the permitted same-subject partial onboarding. The existing profile-role trigger, unique constraints, and foreign keys remain active.
5. Commit only after both rows succeed. A profile failure rolls back the user row.

The service should map a relevant unique-email `P2002`—including a concurrent insert after the pre-read—to a generic 409 `CONFLICT`. It should map provider unavailability to 503 `DEPENDENCY_UNAVAILABLE` only in flows that actually call a provider adapter; the recommended offline API onboarding path has no provider network call. Unexpected persistence failures become safe 500 `INTERNAL_ERROR`. No mapping may expose SQL, credentials, `authSubject`, or provider response text.

### Offline Test Strategy and Evidence Limits

- Unit-test the service with a fake Prisma client whose `$transaction` executes the callback and whose model methods record calls. Assert one transaction, active-district filtering/lock intent, normalized email, `CLIENT` role, complete profile data, and no password field.
- Test a fake unique-email `P2002` both after the pre-read and during the transaction; both cases must produce a safe 409 problem when exercised through `server.inject`.
- Test missing and inactive districts as 422 field errors, database-unavailable failures as safe 503 where applicable, and profile failure as a rejected transaction with no committed fake state.
- Test the auth-port boundary with verified identity, unverified identity, and unavailable-provider fakes. The unverified case must not create an operational domain identity; no live Supabase call is made.
- Add injection coverage for the exact JSON response, content type, trace correlation, validation errors, duplicate conflict, and absence of sensitive values. Extend `createApp` or the Nest test module only enough to replace the auth port and Prisma seam; production bootstrap must keep lazy, dependency-free initialization.
- Regenerate and validate OpenAPI, regenerate the client, run contract freshness/typecheck, and preserve the existing offline test/build gates.

These tests prove application orchestration and fake-client behavior only. They do not prove PostgreSQL trigger execution, FK enforcement, row-lock behavior, migration application, Supabase signup, email delivery, verification, or deployed BFF behavior. Those remain recorded pending gates.

### Recommendation

Proceed with Approach 1 and define this slice as a client onboarding API plus transactional domain persistence. Keep Supabase Auth creation and verification outside the API transaction and outside this implementation until the provider/BFF seam is available; represent it with an explicit injectable port and fake identity adapter. The API must create or reconcile the `CLIENT` user and complete client profile atomically, validate an active district inside that transaction, use normalized email plus database uniqueness for safe 409 handling, and preserve the existing role/FK triggers.

Do not add Auth admin environment variables, a password column, web pages, login/session code, or technician-specific behavior. The proposal must freeze the route, trusted identity context, normalization rule, same-subject idempotency response, and whether this client slice is one work unit within the broader client-and-technician wording of #12. It must record that end-to-end Supabase verification and live PostgreSQL evidence remain pending rather than presenting fake tests as provider acceptance.

### Risks

- **Auth seam honesty:** an offline fake can prove the API transaction but cannot prove Supabase signup, verification, token claims, or BFF ordering. Treat the real provider adapter as deferred and fail safely when unavailable.
- **External/database split:** an API-first provider call can leave an orphan Auth account after database failure. The recommended verified-onboarding order avoids putting a network call inside the transaction, but partial Auth-to-domain reconciliation still needs explicit retry semantics.
- **Email normalization drift:** provider canonicalization, API comparison, and the stored email copy can disagree. One shared, frozen normalization rule is required.
- **Duplicate races:** a pre-read is not a uniqueness guarantee. A targeted `P2002` mapper and a generic problem response are mandatory.
- **Inactive district races:** the current FK proves existence, not active status. Revalidate inside the transaction and use a short district row lock if catalog updates can race.
- **Required profile columns:** the existing schema does not support partial client-profile rows. Registration must create a complete profile or explicitly model partial onboarding in a later schema decision.
- **Offline limits:** no current test can prove PostgreSQL transaction rollback, triggers, FKs, locks, Supabase availability, email delivery, or the pending cloud gate.
- **Contract churn:** adding decorators and new error responses changes both committed OpenAPI artifacts; export, generation, validation, freshness, compatibility, and client typecheck must be run together.
- **Scope creep:** adding the BFF, login/session, profile editing, technician specialties, or UI would merge downstream backlog items into #12 and enlarge review risk.

### Ready for Proposal

Yes. The persistence boundary, active-district rule, duplicate-email behavior, transaction shape, provider seam, offline evidence limits, and affected artifacts are clear enough for proposal work. The proposal should adopt the verified-onboarding recommendation, freeze the API route and idempotency semantics, keep the client-only work unit bounded, and explicitly record Supabase/live-PostgreSQL acceptance as pending.
